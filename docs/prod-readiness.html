Release Gate

Do not deploy as a real production app until these gates pass.

  • npm run build succeeds for the frontend.
  • cd server && npm run build succeeds, as it does now.
  • Frontend and backend test suites pass in clean installs with Node 22.
  • Lint runs only against intended source files and passes.
  • Playwright covers signup, login, create project, add todo, complete milestone, log journal, connect/share flows, and public share view.
  • OAuth, email, AI, GitHub import, cron jobs, and migrations are smoke-tested against staging services.

Vercel Deployment Plan

Best fit

Use Vercel for the React frontend. Keep the Express API on a persistent Node host or VPS unless the backend is refactored into serverless handlers and cron-safe jobs.

1

Create managed Postgres, preferably Neon/Supabase/RDS. Set DATABASE_URL, run Drizzle migrations from CI or a one-off release command.

2

Set frontend env/build: Vercel project root at repo root, build command npm run build, output dist. Add production API base URL support instead of relying only on the Vite dev proxy.

3

Deploy backend separately as a Node service if avoiding refactor. Configure BACKEND_URL, FRONTEND_URL, OAuth callback URLs, JWT secrets, encryption key, Resend, and provider keys.

4

If forcing all-in Vercel, create API route adapters, remove long-lived process assumptions, move cron jobs to Vercel Cron, and make GitHub/reminder jobs idempotent.

5

Add CI checks before Vercel deploy: install frontend and server dependencies, typecheck, lint, unit tests, backend build, frontend build, then Playwright against preview.

6

Promote preview to production only after OAuth callbacks, cookies, CORS, public share URLs, email links, and AI/GitHub flows pass on the preview domain.

VPS Deployment Plan

Best fit

VPS hosting is the least refactor path because the backend is a normal Express server with startup jobs and cron scheduling.

1

Provision a VPS with Ubuntu LTS, a non-root deploy user, firewall rules for SSH/HTTP/HTTPS, automatic security updates, DNS for app.gitshipdone.com, and TLS through Caddy or Nginx plus Certbot.

2

Use managed Postgres if possible. If Postgres runs on the VPS, place it on a persistent volume, restrict it to localhost, schedule encrypted off-server backups, and test restore before launch.

3

Add Dockerfiles: one static web container for dist or a Caddy/Nginx static site, and one Node 22 backend container that runs node dist/index.js. Add a migration command that runs before each deploy.

4

Deploy with Docker Compose or systemd. Run one backend process if cron stays in-process; if scaling later, split reminders and GitHub sync into a dedicated worker so jobs do not duplicate.

5

Configure the reverse proxy: serve frontend assets, proxy /api to the backend, enforce HTTPS, set upload/body limits, and allow only the production frontend origin through CORS.

6

Add observability: structured logs, request IDs, error tracking, disk/CPU/RAM checks, DB metrics, job success/failure metrics, uptime checks, and alert routes.

7

Release through staging first, migrate database, smoke test, take backup, then deploy production with a rollbackable image tag or previous release directory.

Recommended Path

Ship the first production version as Vercel frontend + VPS-hosted Node backend + managed Postgres. That gives the frontend a fast hosted workflow while preserving the backend’s current Express and cron architecture. A single VPS can also host both frontend and backend once Dockerfiles, reverse proxy config, backups, and deploy scripts are in place.
